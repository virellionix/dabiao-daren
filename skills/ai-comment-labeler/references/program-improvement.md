# 已有打标程序：诊断与改进

用于用户交付脚本、标注输出、标签树或客户错标反馈的任务。目标是改进现有业务输出，不是给旧程序另加一套无关分类。仅要求诊断时不改程序；要求修复时在已确认的版本和范围内实现。

## 对齐实际对象

- 找到原脚本、入口/调用者、对应规则版本、代表性输入和输出列。区分原始附件、迁移后的实现和线上实际版本；不要把附件中的缺陷直接描述成已经确认的线上事故。
- 从任务说明、现有产品库、本品/竞品字段和数据辨识项目目标、别名及输入单位。大量数据可帮助发现候选品牌，但出现最多不等于客户指定目标；单条评价对象仍逐条判断。
- 对照客户标签树和程序实际标签集合，查清父子层级、单选/多选、优先级是否一致。账号身份、内容目的、评价对象、态度是不同事实；营销措辞不能单独证明商业合作，账号身份也不能代替每篇内容判断。
- 先保留交付字段和上下游兼容性。内部可以拆开判断多个维度，最后按已确认的规则映射回旧标签；映射有损时说明，不悄悄改客户统计口径。

## 查错，而非只加提示词

沿“原始材料 → 实际模型输入 → 原始模型返回 → 解析/覆盖规则 → 导出”定位第一次出现错误的位置。优先看客户指出的错例及易混类别，不必为每个历史标签找齐样本。

1. **输入缺口**：程序是否真的传入标题、正文、父评论、图文信息、作者资料，而不是输入表有列却未使用。根据具体疑点从用户提供或已授权可读的来源补取；按笔记 ID、评论 ID、父 ID 核对关系，同一原文复用读取结果。图片描述/OCR 与原文分开标记，缺图不能编造图片证据。
2. **规则冲突**：检查“某类最高优先级”和后文例外、强关键词覆盖、先后路由导致另一类别不可达、整篇正负面覆盖具体品牌态度等。用最小对照例说明冲突；业务无法推定的取舍才交给用户。
3. **解析或后处理改错**：检查字符串布尔值、缺字段、非法标签、模型拒答、超时和空结果。无效返回应成为明确错误或待复核，不能默认为正常类、中性、无负面或否。区分语义不确定与接口失败。
4. **判定本身错误**：在输入与规则均充分后再检查语义误判。评论在抱怨广告、商家或竞品时，不能凭项目主要品牌将负面归给本品；引用他人或假设情形不等于作者实际经历。

一次跑出结构化 JSON、没有报错或模型自评 high，都不证明判断准确。先修复已复现的具体环节；不要用更换模型掩盖缺上下文或代码覆盖错误。

## 修复与验证

- 保留旧脚本和旧结果；在用户指定仓库或隔离副本中改动，避免直接覆盖原附件。安装本 Skill 不会让独立脚本自动遵循它，必须明确修改实际提示词、输入构造、解析器或调用链。
- 能离线验证的解析、映射和输入构造问题，用固定模拟返回或本地夹具复现，不为检查代码逻辑调用收费模型。不要运行带真实凭证、安装动作、抓取或部署副作用的旧脚本来做静态检查。
- 比较旧版与新版时固定输入、规则和可比模型设置；若新版本多了上下文，单独标出，不能把所有变化都归功于新提示词。验证新旧结果的行 ID、证据、层级一致性及下游导出。
- 客户纠错可作为对应口径的人工参考，但只对实际确认的条目有效。规则开发用例和最终评测样本分开；没有人工参考时可交付已复现缺陷、离线回归和候选改标，不报准确率提升百分比。
- 交付说明改的是哪个版本、已修环节、旧新例子、未验证范围和是否部署。缺客户错例仅阻止客户准确率结论，不阻止修复明确的解析错误；缺真实采集授权只暂停依赖采集的部分。
